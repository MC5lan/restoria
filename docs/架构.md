# 架构说明

> 目标读者：接手维护的人。
> 原则：**单文件、零依赖、Win7 自带 .NET 4.x + GDI+** 这条底线不能破；"生产级"体现在错误处理、
> 可测性、模块边界和交互细节上，而不是把程序拆成一堆 DLL。

`MainForm` 拆成 22 个 `partial` 文件、`DocClean` 拆成 8 个，共用同一个类（私有成员照旧互相可见），
所以拆分是**纯物理的**，编译产物行为不变。

## 二、依赖方向（单向，不要反向引用）

```
Ui  ──→  Imaging / Ai / Platform / Core
Ai  ──→  Platform（SysInfo）
Imaging ──→  Platform（少量）
Platform ──→  （无）
Core ──→  全部（只读调用，用于自检）
```

- `Imaging` 与 `Ai` 里 **不允许**出现 `System.Windows.Forms`（仅 `ProgressHandler` 这类委托例外）。
- 界面状态一律放 `Ui`；算法只接收参数、返回新位图，不改全局状态。
- 新算法一律走 `BitmapBridge`（LockBits 唯一入口）；倾斜检测绝不隔行采样（混叠会把 0° 顶成最高分）。

## 三、构建、自检与回归协议（改代码必跑）

```bat
build.bat                                    :: 编译（产物 dist\PicTool.exe）
dist\PicTool.exe --selftest                  :: ① 算法自检（退出码 0 = 全过）
dist\PicTool.exe --layout                    :: ② 布局快照（与基线逐行对比）
python tools\check_resources.py --strict     :: ③ 资源门禁（LockBits 配对）
python tools\gate.py                         :: ④ 总门禁（自检 + 布局基线 + AI 产物 + 性能冒烟）
```

改动前后对比 `--layout-check` 的输出（应为逐行一致）与 `--ai-fill` 产物（应为逐像素一致），
是"行为零变化"的客观证据。`--layout-check` 有差异时退出码 1，所以它能卡住构建；
`--layout` 只导出快照、退出码恒 0，仅供人工查看。
UI 有意变更时用 `--regen-layout` 重新生成基线。

## 四、关键设计决策

### AI 加载隔离

启动路径上永远不加载 `onnxruntime.dll`（`Available` 只看文件、`StatusText` 是廉价文本）；
真正加载前先拉子进程 `--ort-probe` 去试，父进程读不到结果文件就判定"本机不安全"，永不加载。
整个程序不会因为 AI 打不开而受影响。

### Win7 兼容（onnxruntime 垫片）

Win7的 kernel32 没有 `CreateFile2`/`PathCch*`/`GetSystemTimePreciseAsFileTime`/`EventSetInformation`，
原版 onnxruntime.dll 一加载就是"无法定位程序输入点"。

做法：把这 4 个 API 集名在**导入表**里改成普通文件名（`w7shim-*.dll`），垫片用这个名字发出去。
这 4 个是必须的——加载器对 `api-ms-win-*` 用内置 API 集 schema 解析、不查文件系统，
同名 dll 放旁边根本不会被命中，改成普通文件名才走文件搜索、必然命中自己的实现。

分两套运行时：

- `ai\onnxruntime.dll`：原版，Win8/10/11 用，零垫片
- `ai\win7\onnxruntime.dll`：补丁版，Win7 用

`ai\win7\` 里有 **20 个 `api-ms-win-core-*.dll`**，它们和上面 4 个 w7shim 性质不同，不是"改名绕开
schema"的补丁，而是**兜底副本**：Win7 自带的 API 集没有覆盖onnxruntime 导入的全部条目，
放同名文件在旁边是在这些条目上给加载器一个可解析的落点。Win8+ 上它们是多余的（系统 schema 直接
解析，`tools\ProbeShim.cs` 实测去掉后仍能加载），但 Win7 上是唯一来源。

**这 20 个必须与补丁版 dll 同目录一起分发。** 少一个就可能"无法定位程序输入点"，
而症状和缺 w7shim 完全一样，排查时容易误判成垫片不全。

程序按"谁能加载用谁"依次试，不做系统版本判断——失败廉价且无副作用，比猜版本可靠。

## 布局基线（--layout / --layout-check）

**它能分辨多小的变化？** 已实测：`tools\LayoutGateProbe.bat` 把一个控件的宽度
从 204 改成 205，快照第 7 行随之变化，门禁判为差异。

```
before: TextBox '' bounds={X=20,Y=52,Width=204,Height=14}
after : TextBox '' bounds={X=20,Y=52,Width=205,Height=14}
```

所以 1px 是能被抓到的。探针的意义就在这里：以前"行为零变化"这句话是断言，
现在有可运行的证据（`LayoutGateProbe.exe` 退出码 0 = 敏感度合格）。

**注意**：探针只能移动 `Dock=None` 的控件。docked 控件的位置由 `PerformLayout()`
重算，推它一下会被布局引擎原样还原——那样测出来的"没差异"是探针的失败，
不是门禁的失败。第一次跑就踩了这个坑（挪 CanvasControl 得到假阴性）。

### 两个曾让这道门禁形同虚设的缺陷（2026-10-19 修）

**① 快照里写了随机器变化的环境行。** 第 2 行原本是
`环境: RAM 16236MB, 64 位进程, 12 核, 并行 8, …CLR 4.0.30319.42000`。
RAM 和核数每台机器都不同，等于把基线与生成它的那台机器绑定 ——
在任何第二台机器（包括 CI）上必然假报警，而那行差异与代码毫无关系。
现在固定写成 `环境: (随机器变化，详见 PicTool-env.txt)`；具体值由
`WriteEnvReport()` 写到 `%TEMP%\PicTool-env.txt`，内容比这一行详细得多。

**② `--layout` 从不设退出码。** 以前 CI 里写的是

```bat
dist\PicTool.exe --layout
if errorlevel 1 (exit /b 1)
```

但 `--layout` 只是导出快照然后 `return`，退出码恒为 0，那句判断永远不触发。
**这一步在 CI 上一直是"绿的空壳"** —— 看着有个布局门禁，实际什么都没查。
真正的比较在 `gate.py` 里，而那一步是 `continue-on-error: true`，同样不阻断。
合起来：布局门禁从来没有拦住过任何一次提交。

现在把两种用法分开：

| 参数 | 行为 | 退出码 |
|---|---|---|
| `--layout` | 只导出快照，不比较 | 恒 0（供人工查看） |
| `--layout-check` | 导出快照，与 `tools\golden-layout.txt` 逐行比较 | 一致 0，有差异 1 |

CI 改用 `--layout-check`，是真正会红的步骤。它**只读基线，绝不自动改基线** ——
门禁自己把基线改成当前状态的话，它就永远通过，也就失去意义。基线只能由
`gate.py --regen-layout` 显式重建。

验证方式（`probe_layoutcheck.ps1`）：干净时退出 0；把基线里的 `1080x680`
改成 `1080x681` 后退出 1 并打印差异行。

### ③ 快照记录了字体度量结果（跨机器必然失配）

前两个缺陷修好、门禁真的开始检查之后，CI 立刻红了 —— 而且只有布局这一步红，
自检 134 项、资源门禁、性能全部通过。这说明红的原因是环境，不是代码。

根因用 `tools\MeasureFont.bat` 量出来了。同一句页面说明文字：

| 字体 | 测量尺寸 | Font.Height |
|---|---|---|
| Microsoft YaHei UI | 219 × 15 | 14 |
| Microsoft YaHei | 219 × 16 | 15 |
| Segoe UI | **229 × 16** | **15** |

`Theme.PickFace()` 的候选顺序是 微软雅黑 → Segoe UI，而 GitHub 的
`windows-latest` 是英文镜像、**没有装微软雅黑**，于是回退到 Segoe UI：
文字宽 10px、高 1px。`PageHead()` 里 `y += s.Height + 12` 把这个 1px
放大成整页后续控件的整体偏移 —— 基线在一台机器生成、在另一台必然对不上。

三条修法，都只影响诊断模式，**产品运行时的外观完全不变**：

1. `MainForm.DeterministicLayout` 开关，由 `--layout` / `--layout-check` 置位。
   它打开时，`PageHead()` 的说明标签不用 AutoSize，改用常量高度 18。
   这样 `y` 的累加与字体度量无关，任何机器算出同一个数。
2. `DumpCtrl()` 对 AutoSize 控件的 Height 记录为 `auto` 而不是实际像素。
   （TextBox 也是 AutoSize，高度同样随字体变：14 vs 15。）
3. `PICTOOL_UI_FACE` 环境变量可以强制指定界面字体 —— 没有它就无法在单机上
   复现"另一台机器的字体"，也就无法验证前两条是否真的有效。

**验证**（`test_font_immunity.ps1`）：默认字体、强制 Segoe UI、强制雅黑三种
情况下，快照 SHA256 完全相同（`AC953E8FE193CF8E`），三次都退出 0。
同时 `LayoutGateProbe` 仍然能抓到 1px 改动（1 行差异）—— 说明一致性的提高
没有牺牲灵敏度。

**代价要写清楚**：快照现在反映的是"布局逻辑"（Dock、间距、控件树、顺序、
固定尺寸），不是"像素级渲染结果"。AutoSize 控件因文字换行产生的高度差异
被标准化掉了。想验证真实渲染差异，看 `--shot` 的截图，不要指望布局快照。

**探针自身的坑**：`LayoutGateProbe` 用反射建窗体，绕过了 `Program.Main` 的
`--layout` 分支，所以一开始没开确定性模式 —— 测出来 172 行差异，全是它自己
造成的假象。它现在显式通过反射置位该开关。凡是"自己造窗体"的探针都要记得
补这一步，否则测的不是门禁看的那份快照。

### 倾斜检测：黑边保险

带黑边的图（旋转没自动裁边留下的黑角、扫描仪黑背景露边）会被投影法当成墨迹带偏
（实测：同一张 -3° 的图，无保险时 12/12 全判 0°）。对策两步，且只在确实有黑边时才动手：

1. 量画面外圈 2px 里"接近纯黑"（灰度<70）的比例，≥15% 才认为有黑边。
   用**绝对灰度线**而不是 Otsu 阈值——文字多的页 Otsu 阈值偏高，会把偏灰的纸边也算成墨而误触发。
2. 有黑边时把"与边框 4 连通的暗块"整块排除（黑角/黑框无论多宽都一次去干净）。

检测范围 ±20°（投影桶只有 1px 宽、偏移量是整数，放宽只影响数组长度、不影响分数）。

### 纸面重建（PaperFill）

不含任何生成——用涂抹区周围的纸面重建一片干净纸。五步：两遍分块背景估计 →
按经验分布重采样纸纹 → 边界取"环上纸面真实残差"解调和平差 → **直线续接**（把横穿涂抹区的
表格线/边框接回去）→ 掩膜外扩（6px + 6%，上限 20px）后羽化合成。

直线续接的判据（三条缺一不可，宁可漏判也不误画）：①该行/列已知部分里"墨"的占比 ≥ 55%；
②洞的两侧都有墨（确实横穿）；③墨的断口 ≤ 6——表格线只有洞这一个断口，一行文字有几十个，
这条是区分"线"和"字"的关键。颜色取已知部分的中位色。

### 模型选型结论

| 模型 | 结论 |
|---|---|
| MI-GAN 28MB（现用） | 保留。指标与纸面重建相当；长处是能把表格线这类长直线延伸过去，短处是洞里会留灰色块状糊斑 |
| LaMa 208MB | **弃用**。质量上色调偏灰绿；且 ORT 1.14 的 CPU 内核跑不了它的 FFT 结构（多线程访问冲突打死进程）。1.14.1 恰恰是 Win7 能用的最后一版 |

换模型前先跑 `python tools\onnx_ops.py --diff ai\migan.onnx 候选.onnx` 核对算子兼容性。

### 极致档方向检测

OCR 只判 90/270，180° 一律不认（真实档案实测误转端正页比漏转更糟——转倒=破坏内容）；
180° 只认装订孔物理证据。

## 五、已知限制

- 针对平面扫描件设计；手机拍照有透视变形，不保证效果
- AI 运行时钉在 ORT 1.14.1（Win7 最后一版）
- 空白页边距上一个孤立的实心字符（如加粗的"●"）会被黑点过滤的 R1 判据删掉——遇到这类档案需改代码
