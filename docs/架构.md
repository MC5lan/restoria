# 架构说明

> 目标读者：接手维护的人。
> 原则：**单文件、零依赖、Win7 自带 .NET 4.x + GDI+** 这条底线不能破；"生产级"体现在错误处理、
> 可测性、模块边界和交互细节上，而不是把程序拆成一堆 DLL。

## 一、源码地图

```

  Core/

    Bench.cs                    性能基准（--bench）
```

`MainForm` 拆成 22 个 `partial` 文件、`DocClean` 拆成 8 个，共用同一个类（私有成员照旧互相可见），
所以拆分是**纯物理的**，编译产物行为不变。

## 二、依赖方向（单向，不要反向引用）

```
Ui  ──→  Imaging / Ai / Platform / Core
Ai  ──→  Platform（SysInfo）
Imaging ──→  Platform（少量）
Platform ──→  （无）
Core ──→  全部（只读调用，用于自检）
```

- `Imaging` 与 `Ai` 里 **不允许**出现 `System.Windows.Forms`（仅 `ProgressHandler` 这类委托例外）。
- 界面状态一律放 `Ui`；算法只接收参数、返回新位图，不改全局状态。
- 新算法一律走 `BitmapBridge`（LockBits 唯一入口）；倾斜检测绝不隔行采样（混叠会把 0° 顶成最高分）。

## 三、构建、自检与回归协议（改代码必跑）

```bat
build.bat                                    :: 编译（产物 dist\PicTool.exe）
dist\PicTool.exe --selftest                  :: ① 算法自检（退出码 0 = 全过）
dist\PicTool.exe --layout                    :: ② 布局快照（与基线逐行对比）
python tools\check_resources.py --strict     :: ③ 资源门禁（LockBits 配对）
python tools\gate.py                         :: ④ 总门禁（自检 + 布局基线 + AI 产物 + 性能冒烟）
```

改动前后对比 `--layout` 输出（应为逐行一致）与 `--ai-fill` 产物（应为逐像素一致），
是"行为零变化"的客观证据。UI 有意变更时用 `--regen-layout` 重新生成基线。

## 四、关键设计决策

### AI 加载隔离

启动路径上永远不加载 `onnxruntime.dll`（`Available` 只看文件、`StatusText` 是廉价文本）；
真正加载前先拉子进程 `--ort-probe` 去试，父进程读不到结果文件就判定"本机不安全"，永不加载。
整个程序不会因为 AI 打不开而受影响。

### Win7 兼容（onnxruntime 垫片）

Win7的 kernel32 没有 `CreateFile2`/`PathCch*`/`GetSystemTimePreciseAsFileTime`/`EventSetInformation`，
原版 onnxruntime.dll 一加载就是"无法定位程序输入点"。

做法：把这 4 个 API 集名在**导入表**里改成普通文件名（`w7shim-*.dll`），垫片用这个名字发出去。
这 4 个是必须的——加载器对 `api-ms-win-*` 用内置 API 集 schema 解析、不查文件系统，
同名 dll 放旁边根本不会被命中，改成普通文件名才走文件搜索、必然命中自己的实现。

分两套运行时：

- `ai\onnxruntime.dll`：原版，Win8/10/11 用，零垫片
- `ai\win7\onnxruntime.dll`：补丁版，Win7 用

`ai\win7\` 里有 **20 个 `api-ms-win-core-*.dll`**，它们和上面 4 个 w7shim 性质不同，不是"改名绕开
schema"的补丁，而是**兜底副本**：Win7 自带的 API 集没有覆盖onnxruntime 导入的全部条目，
放同名文件在旁边是在这些条目上给加载器一个可解析的落点。Win8+ 上它们是多余的（系统 schema 直接
解析，`tools\ProbeShim.cs` 实测去掉后仍能加载），但 Win7 上是唯一来源。

**这 20 个必须与补丁版 dll 同目录一起分发。** 少一个就可能"无法定位程序输入点"，
而症状和缺 w7shim 完全一样，排查时容易误判成垫片不全。

程序按"谁能加载用谁"依次试，不做系统版本判断——失败廉价且无副作用，比猜版本可靠。

### 倾斜检测：黑边保险

带黑边的图（旋转没自动裁边留下的黑角、扫描仪黑背景露边）会被投影法当成墨迹带偏
（实测：同一张 -3° 的图，无保险时 12/12 全判 0°）。对策两步，且只在确实有黑边时才动手：

1. 量画面外圈 2px 里"接近纯黑"（灰度<70）的比例，≥15% 才认为有黑边。
   用**绝对灰度线**而不是 Otsu 阈值——文字多的页 Otsu 阈值偏高，会把偏灰的纸边也算成墨而误触发。
2. 有黑边时把"与边框 4 连通的暗块"整块排除（黑角/黑框无论多宽都一次去干净）。

检测范围 ±20°（投影桶只有 1px 宽、偏移量是整数，放宽只影响数组长度、不影响分数）。

### 纸面重建（PaperFill）

不含任何生成——用涂抹区周围的纸面重建一片干净纸。五步：两遍分块背景估计 →
按经验分布重采样纸纹 → 边界取"环上纸面真实残差"解调和平差 → **直线续接**（把横穿涂抹区的
表格线/边框接回去）→ 掩膜外扩（6px + 6%，上限 20px）后羽化合成。

直线续接的判据（三条缺一不可，宁可漏判也不误画）：①该行/列已知部分里"墨"的占比 ≥ 55%；
②洞的两侧都有墨（确实横穿）；③墨的断口 ≤ 6——表格线只有洞这一个断口，一行文字有几十个，
这条是区分"线"和"字"的关键。颜色取已知部分的中位色。

### 模型选型结论

| 模型 | 结论 |
|---|---|
| MI-GAN 28MB（现用） | 保留。指标与纸面重建相当；长处是能把表格线这类长直线延伸过去，短处是洞里会留灰色块状糊斑 |
| LaMa 208MB | **弃用**。质量上色调偏灰绿；且 ORT 1.14 的 CPU 内核跑不了它的 FFT 结构（多线程访问冲突打死进程）。1.14.1 恰恰是 Win7 能用的最后一版 |

换模型前先跑 `python tools\onnx_ops.py --diff ai\migan.onnx 候选.onnx` 核对算子兼容性。

### 极致档方向检测

OCR 只判 90/270，180° 一律不认（真实档案实测误转端正页比漏转更糟——转倒=破坏内容）；
180° 只认装订孔物理证据。

## 五、已知限制

- 针对平面扫描件设计；手机拍照有透视变形，不保证效果
- AI 运行时钉在 ORT 1.14.1（Win7 最后一版）
- 空白页边距上一个孤立的实心字符（如加粗的"●"）会被黑点过滤的 R1 判据删掉——遇到这类档案需改代码
